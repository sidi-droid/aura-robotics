01Project Overview & Vision

AURA (Autonomous Utility Rover Architecture) is a modular AI-powered autonomous mobile robotics platform designed for intelligent indoor navigation and future robotic manipulation.

Unlike traditional autonomous cars that perform only one task, AURA is designed as a complete robotics platform capable of mapping, localization, obstacle avoidance, person detection, mission execution and future teleoperation. The platform is designed from the ground up to be modular, so that additional systems such as robotic arms, teleoperation, exoskeleton control and AI assistants can be added without redesigning the entire robot.

Project Objective

To develop a fully autonomous six-wheel mobile robotics platform capable of:

Autonomous indoor navigation SLAM Multi-sensor perception Dynamic obstacle avoidance Autonomous path planning Person detection Person following Mission execution Manual override

Problem Statement

Current educational autonomous vehicle projects generally focus on a single capability such as lane following, parking or obstacle avoidance. The objective of AURA is to build a complete robotics platform capable of understanding unknown indoor environments, creating maps, localizing itself, planning safe paths and autonomously executing missions — while remaining modular for future research in manipulation and human-robot interaction.

Final Project Goal

AURA is not intended to be just another autonomous vehicle. It is designed as a long-term modular robotics platform that begins as an intelligent autonomous rover and gradually evolves into a fully capable mobile manipulator with teleoperation, AI-assisted autonomy and learning capabilities. The modular engineering approach allows future upgrades without redesigning the mobility platform, making it suitable for continued development throughout the remainder of the undergraduate program and beyond.

The robot detects an unknown environment and begins autonomous exploration. LiDAR builds a map while the RealSense supplies depth information, and the IMU and encoders refine localization. The generated map is saved, and the user labels important locations — for example: Classroom 401, Classroom 402, Robotics Lab, Charging Station, Main Entrance. These names are permanently stored.

09Development Workflow (Simulation-to-Real)

AURA will follow an industry-standard Simulation-to-Real (Sim-to-Real) development workflow. Instead of developing directly on hardware, every major subsystem will first be designed, tested and validated in simulation before deployment to the physical robot. This approach minimizes hardware damage, reduces debugging time and enables parallel software and mechanical development.

Phase 0 — Digital Twin

Before assembling the physical robot, a complete virtual representation (Digital Twin) of AURA will be created. This allows software development to begin immediately, even before all hardware components have arrived. This phase includes finalizing the system architecture; designing the chassis and mechanical components in Fusion 360; creating the robot description using URDF/Xacro; simulating sensors including LiDAR, Intel RealSense, IMU and wheel encoders; testing SLAM, localization, navigation and obstacle avoidance in simulation; and verifying software before hardware assembly.

Conduct progressive testing: motor testing, sensor validation, indoor mapping, localization, autonomous navigation, dynamic obstacle avoidance, person detection, person following and return-to-home. Each subsystem is validated independently before full autonomous operation.

21Multi-Camera Perception Architecture

For fluid manipulation, cameras must run simultaneously — never one replacing another. Switching cameras, even for a second, would make the manipulation experience feel terrible. The architecture is therefore designed so all cameras stream at once and the system simply changes which camera is prioritized for a given task.

Jetson Orin Nano
▼
RealSense Camera Left Wrist Camera Right Wrist Camera
▼
Perception & Fusion Layer
▼
Mission / Manipulation

What Happens During a Pick

  1. RealSense detects the bottle from across the room.
  2. Robot navigates to the table.
  3. As the arm approaches, the wrist camera is already streaming.
  4. The manipulation software starts using the wrist camera for fine alignment.
  5. The RealSense doesn't stop — it continues monitoring the overall scene for people, obstacles and changes.

There is no "camera switch." It is a change in which camera is given priority, with every input available at the same time:

SourceConcurrent Signal
RealSense"The bottle is on the table."
Wrist camera"The gripper is 15 mm too far left."
IMU + encoders"The robot is stable."
Joint encoders"The arm is at the correct pose."

Can the Jetson Orin Nano Handle This?

Yes — provided the workload is managed sensibly. Heavy AI inference does not need to run on every camera at full resolution all the time:

  • RealSense — navigation and global perception (always on).
  • Left wrist camera — processed only when the left arm is manipulating.
  • Right wrist camera — processed only when the right arm is manipulating.

Recommendation — A Perception Manager

Rather than cameras feeding directly into robot logic, route them through a dedicated Perception Manager:

Cameras
▼
Perception Manager
▼
Mission Manager
▼
Navigation / Arms

The Perception Manager decides which camera(s) to use for navigation, which to use for grasping, and when to fuse information from multiple cameras.

The "One Organism" Behavior

The robot never "switches eyes." It uses whichever eyes are most useful for the current task while keeping the others available in the background — behaving as a single coordinated organism rather than a set of competing sensors.

24Long-Term Vision & Project Philosophy

AURA is designed as a modular robotics platform rather than a single-semester project. Future upgrades will include robotic manipulation, immersive teleoperation, wearable exoskeleton control, offline conversational AI and Learning from Demonstration — all while preserving the same mobility platform and software architecture. The objective is to continue developing AURA throughout the remainder of the undergraduate program into a research-grade autonomous mobile manipulation platform.

Build once. Upgrade forever.

Every hardware and software decision should prioritize modularity, maintainability and future expansion. No subsystem should require redesign simply to add new capabilities. The robot should evolve through plug-and-play modules while preserving a stable, reliable autonomous core.
